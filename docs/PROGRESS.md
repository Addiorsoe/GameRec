## GameRec 目前功能

- 選擇目標程式（自動抓主視窗），記憶體監看清單：絕對位址、`模組+偏移`、指標鏈（`game.exe+0x10,0x8` 或 `0x1234,0x10`）
- 同步記錄：記憶體（30Hz，變動才寫）、封包（只留該程式的連線）、視窗錄影（每幀時間戳）、鍵鼠事件、標記
- 熱鍵（可自訂）：鎖定目前視窗 `F8`、開始/停止 `F9`（停止即匯出，不跳視窗）、加標記 `F10`；強制停止 `Ctrl+Alt+End`（固定）；按住不放只算一下
- 每段錄製選組別，檔名自動加組別與流水號（`_A-01_`、`_A-02_`…）；備註可錄前填或事後「更新上一段的備註」
- 環境檢查視窗：Windows 10/11、64 位元、管理員、Npcap、新版本；電腦規格（處理器、記憶體、顯示卡、螢幕、硬碟、BIOS 虛擬化），第一次啟動掃描一次並存檔，之後直接讀檔，可按「重新掃描」
- 輸出資料夾預設 `文件\GameRec\sessions`

## 資料可判讀性

匯出 zip 內每個檔案都附在 `README.txt` 說明；全部用同一個 `t_ns`（距開始的奈秒）對齊。

| 檔案 | 格式 | 範例 |
|---|---|---|
| `memory/samples.csv` | `t_ns,name,value` | `523400100,player_x,12.5` |
| `network/packets.jsonl` | 每行一個 JSON | `{"t_ns":710316312,"dir":"out","proto":"udp","src":"127.0.0.1","sport":57703,"dst":"127.0.0.1","dport":47000,"len":6,"payload_hex":"706f73203235","payload_ascii":"pos 25"}` |
| `input/events.jsonl` | 每行一個 JSON | `{"t_ns":2400000000,"kind":"key_down","key":"w"}` |
| `markers.jsonl` | 每行一個 JSON | `{"t_ns":2423013100,"label":"walk north"}` |
| `video/frames.csv` | `frame,t_ns,left,top,width,height,source,dup` | 第幾幀對應哪個時間；`source`=實際錄到的範圍（window/screen）；`dup=1` 表示截圖跟不上而重複上一幀 |

CI 每次都會解析全部 JSONL / CSV 並印出樣本；封包內容在 Linux 實測（Windows CI 沒有 Npcap）。

## 複查結果（2026-11-25）

做法：逐檔讀程式碼，每個懷疑點先寫測試**重現**，重現得出來才算問題、才修；重現不出來就記為「沒問題」。修好後同一個測試轉為通過，留在 `tests/test_audit.py`、`tests/test_video_pacing.py` 長期防回歸。

### 確認存在並已修正（11 項）

| # | 問題 | 修正前的證據 | 修正後 |
|---|---|---|---|
| 1 | 封包誤判：只比對埠號，別的程式剛好用到同一個埠也會被算成目標的封包 | 測試中另一程式的流量被標成 `in` | 以（協定, 本機 IP, 埠）比對，萬用位址才比對本機所有 IP |
| 2 | 新連線最前面的封包遺失（埠清單每秒才更新） | 新連線的前幾個封包不在輸出中 | 未知封包暫存 1.5 秒（上限 5000），埠清單更新後補判 |
| 3 | 目標程式關閉後，舊埠仍被當成目標的 | 程式結束後同埠的新流量仍被收錄 | 偵測到程式結束即清空 |
| 4 | 記憶體：指標鏈斷掉時保留舊值，看起來像數值沒變 | 讀取失敗後 CSV 仍是 `1.0` | 讀不到就寫空值，一眼看出斷線 |
| 5 | float 精度：`1e-7` 被寫成 `0.0` | 測試輸出 `0.0` | float 取 9 位有效數字、double 不再四捨五入 |
| 6 | 監看清單允許重複名稱，兩個位址混在同一欄 | 重複名稱被接受 | 新增、匯入都會拒絕並提示 |
| 7 | 同一秒開始兩次錄製會寫進同一個資料夾互相覆蓋 | 兩個 session 資料夾相同 | 自動加 `_2`、`_3` |
| 8 | 按鍵記錄：Ctrl+A 被記成 `\x01`；長按的自動重複分不出來 | 輸出 `'\x01'` | 記成 `a`，重複按鍵加 `"repeat": true` |
| 9 | 熱鍵卡鍵：Alt+Tab 等情況漏掉放開事件，之後每個按鍵都被當成組合鍵 | 測試中修飾鍵永遠卡住 | 每次按主鍵時向 Windows 確認修飾鍵實際狀態 |
| 10 | 影片時間錯誤：截圖慢時影片變短，3.38 秒實際時間只播 1.60 秒 | 測試量到 1.60s / 3.38s | 依實際時間補幀（`dup=1` 標示），影片長度等於實際時間 |
| 11 | 停止錄製時先跳備註視窗才停，你打備註的按鍵也被錄進去；對話框開著時熱鍵還能再觸發停止 | 讀程式碼確認順序 | 先停止再問備註；處理中忽略熱鍵 |

### 可能的惡性循環（已排除）

| 情境 | 修正前 | 現在 |
|---|---|---|
| 程式出錯時錯誤視窗一直跳 | 每次錯誤都跳一個視窗 | 同時只跳一個，5 秒內不重複 |
| 某個熱鍵動作出錯 | 熱鍵輪詢會中斷，之後所有熱鍵失效 | 出錯也會繼續輪詢 |
| 封包暫存區越積越多 | — | 有上限（5000 筆／1.5 秒），超出會在 manifest 記錄 `unmatched_buffer_overflow`，不會吃光記憶體 |
| 影片補幀追不上 | — | 一次最多補 2 秒，不會無限補 |

### 檢查過、沒問題的部分

- 時鐘：所有串流共用同一個單調時鐘，記憶體、按鍵、標記不受系統調時影響
- 記錄器互相隔離：任一個失敗（沒裝 Npcap、截圖失敗）其他照常，manifest 會標示原因
- 強制停止 Ctrl+Alt+End：任何狀態下都能停止並存檔
- 匯出：zip 內容與 manifest 筆數一致

### 移除的冗餘

- 只為測試存在的 Linux 記憶體後端（已刪）
- 未使用的 `local_ports`、按鍵 `on_key` 回呼、舊的封包方向測試
- 封包處理每筆都重新 import scapy 模組 → 改為只載入一次

### 仍存在的限制（如實記錄）

- 封包時間是由系統時間換算；錄製中若系統時間被調整，封包時間會偏移（其他資料不受影響）
- Python 抓包在流量很大時會吃 CPU；遊戲一般流量沒問題
- Windows 上實際用 Npcap 抓包還沒在實機驗證（CI 機器沒有 Npcap）

## 尚未驗證 / 已知限制

- Npcap 實際抓封包只在 Linux 驗證過；Windows 上需要你裝好 Npcap 後實機試一次
- Npcap 免費版沒有靜默安裝，一鍵安裝會開啟官方安裝精靈，需手動按下一步（記得勾 WinPcap 相容模式）
- 真實遊戲可能有反外掛，讀不到記憶體或被偵測
